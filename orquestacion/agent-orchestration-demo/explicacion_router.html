El patrón Router: cómo enruta y ejecuta agentes

Sin LangGraph, sin frameworks: un RouterAgent de ~80 líneas que lee una solicitud, decide qué agente(s) especializado(s) le corresponden por palabra clave, y los corre —en paralelo si hace falta más de uno. Esta explicación sigue el código real de router/.

La diferencia con el pipeline

Camino fijo vs. camino decidido en runtime

El pipeline (pipeline/main.py) siempre corre A1 → A2 → A3, sin importar qué pida el usuario. El router es lo opuesto: no hay una secuencia hardcodeada. El RouterAgent mira el texto de la solicitud, lo compara contra un catálogo de agentes (AGENT_REGISTRY) y decide, recién en ese momento, cuáles de ellos aplican — puede ser uno, varios, o ninguno.

Paso 1

Cómo decide el RouterAgent

La estrategia (v1, deliberadamente simple) es keyword matching: normaliza el texto (minúsculas, sin acentos) y busca, para cada agente del catálogo, si alguna de sus capabilities aparece como substring. Si varias coinciden, selecciona varios agentes a la vez.

Paso 2

Cuando hay más de un agente, corren en paralelo

Si RoutingDecision trae más de un agente, router/main.py no los llama uno tras otro: los envía todos al mismo tiempo a un ThreadPoolExecutor y recién después espera los resultados. Con un LLM real (que tiene latencia de red), esto cambia el tiempo total de "la suma de todos" a "el más lento de todos".

Paso 3

El dato que atraviesa cada etapa

A diferencia del grafo de LangGraph (un único diccionario que se va completando), acá cada etapa produce un tipo distinto de dataclass (definidas en common/models.py). Cada función recibe el tipo anterior y devuelve el siguiente.

Trazado real

Caso 3 paso a paso: "préstamo + inversión"

  1. router.route(solicitud)

    Normaliza el texto y recorre AGENT_REGISTRY. Encuentra "prestamo" en las capabilities de credit_agent y "inversion" en las de investment_agent. Devuelve RoutingDecision(selected_agents=["credit_agent", "investment_agent"], reason="Coincidencias encontradas -> ...").

  2. build_agent_map + selección

    router/main.py arma los agentes con el MockLLM compartido y se queda solo con los dos que eligió el router: selected = [credit_agent, investment_agent].

  3. ThreadPoolExecutor — envío

    Como len(selected) > 1, se abre un pool y se envían los dos agent.run(...) antes de esperar ningún resultado — por eso corren concurrentemente, no uno después del otro.

  4. cada agente corre solo

    Cada SpecialistAgent.run() arma su propio prompt (su PROMPT + la solicitud original), llama a llm.generate(...) y devuelve un AgentResult propio. Ninguno sabe que el otro existe.

  5. Aggregator.aggregate()

    Recibe los dos AgentResult. Como hay más de uno, no devuelve solo el primero: concatena "[credit_agent]\n..." y "[investment_agent]\n..." en un único FinalResponse.answer.

Dato del código: si ninguna capability matchea (por ejemplo, una solicitud sobre el clima), route() devuelve RoutingDecision(selected_agents=[]) y main.py corta ahí — no hay un agente "genérico" de respaldo en esta versión.

Cómo correrlo

Ejecutar la demo

No requiere instalar nada: MockLLM simula el LLM de forma determinística, sin API keys ni red.

cd orquestacion/agent-orchestration-demo
python router/main.py

Corre los 4 casos fijos de router/main.py: préstamo (1 agente), inversión (1 agente), préstamo + inversión (2 agentes en paralelo) y tarjeta (1 agente). La consola imprime, para cada caso: el catálogo disponible, la RoutingDecision con el motivo del match, el arranque y resultado de cada agente, y la FinalResponse agregada.

Referencia

Piezas del código

PiezaQué hace
AGENT_REGISTRYCatálogo de agentes: name, description, capabilities. El router solo lee esta lista, nunca las clases reales.
RouterAgent.route()Normaliza el texto, compara contra las capabilities de cada agente y devuelve una RoutingDecision.
SpecialistAgent.run()Base común: arma el prompt, llama a llm.generate(), mide tiempo y devuelve un AgentResult. Cada subclase solo cambia PROMPT y capabilities.
ThreadPoolExecutorEnvía todos los agent.run() seleccionados a la vez cuando hay más de uno, para que corran en paralelo.
Aggregator.aggregate()Combina uno o varios AgentResult en una FinalResponse. Sin LLM en esta versión: solo concatena.

Más allá de keyword matching

Cómo evoluciona el ruteo

El README del proyecto marca un camino incremental, y en los tres pasos el resto del sistema (agentes, aggregator, main) no cambia — solo cambia adentro de RouterAgent.route():

Router basado en LLM: en vez de buscar substrings, se le pasa al LLM la solicitud + el catálogo (nombre + descripción) y que elija. Entiende frases que no usan la palabra clave exacta ("necesito plata para un auto" → credit_agent).

Embeddings y RAG: se enruta por similitud coseno entre el embedding de la solicitud y el de cada agente; con catálogos grandes, se indexa en una base vectorial y se recuperan solo los candidatos más relevantes antes de decidir.

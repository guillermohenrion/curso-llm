A2A: agentes que se hablan entre procesos distintos

Los tres ejemplos anteriores viven todos adentro de un mismo proceso Python. A2A (Agent2Agent) resuelve un problema distinto: cómo hacen dos agentes que corren en procesos, máquinas o hasta frameworks diferentes para hablarse, sin que uno conozca el código interno del otro. Esta versión usa el SDK oficial (a2a-sdk, del proyecto Agent2Agent / Linux Foundation): nosotros solo escribimos la lógica del agente, todo lo protocolar lo arma el SDK.

La diferencia real

No es "otro patrón de grafo" — es cruzar un proceso

En multiagente_langgraph.py o el generador_critico_langgraph.py, "supervisor" y "agente" son dos funciones de Python en el mismo proceso, que se pasan un diccionario en memoria. En A2A, cada agente es un servicio HTTP aparte: no hay memoria compartida, no hay import — todo lo que un agente sabe del otro es su URL y su Agent Card. Por eso A2A no compite con LangGraph: se puede envolver un grafo entero de LangGraph adentro de un servidor A2A y exponerlo hacia afuera como un agente más.

Las dos piezas

Agent Card (descubrimiento) + JSON-RPC (invocación)

Todo A2A se reduce a dos intercambios HTTP. Primero el cliente descubre al agente pidiendo su Agent Card — un JSON público con su nombre, sus skills y la URL a la que hay que hablarle. Después lo invoca mandándole un mensaje por JSON-RPC 2.0 con el método message/send. La respuesta puede ser un Message directo (agente que contesta al toque, como este) o una Task (agente que queda trabajando en el fondo) — más sobre esa diferencia abajo.

Anatomía del mensaje

Lo que viaja por la red, tal cual

Esto es JSON real capturado corriendo agente_servidor.py / cliente.py — nosotros nunca escribimos estos diccionarios a mano; los arma el SDK a partir de los objetos Python (AgentCard(...), Message(...)).

Agent Card — GET /.well-known/agent-card.json

{
  "name": "traductor_a2a",
  "description": "Traduce frases simples de espanol a ingles (vocabulario de demo).",
  "url": "http://127.0.0.1:9000/",
  "version": "0.1.0",
  "protocolVersion": "0.3.0",
  "preferredTransport": "JSONRPC",
  "capabilities": { "streaming": false },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": [
    { "id": "traducir_es_en", "name": "Traducir espanol a ingles",
      "tags": ["traduccion", "demo"], "examples": ["hola mundo"] }
  ]
}

Request — POST / (JSON-RPC 2.0, método message/send)

{
  "id": "9f2c...", "jsonrpc": "2.0",
  "method": "message/send",
  "params": {
    "message": {
      "kind": "message",
      "messageId": "a1b2...",
      "role": "user",
      "parts": [{ "kind": "text", "text": "hola mundo gracias" }]
    }
  }
}

Response — result es un Message, NO una Task

{
  "id": "9f2c...", "jsonrpc": "2.0",
  "result": {
    "kind": "message",
    "messageId": "c3d4...",
    "role": "agent",
    "parts": [{ "kind": "text", "text": "hello world thank you" }]
  }
}

Esto sorprendió incluso escribiendo la demo: la primera versión de este ejemplo (hecha a mano, sin el SDK) siempre envolvía la respuesta en una Task con artifacts — parecía "más completo". Pero el spec real dice otra cosa: un agente que responde al toque (como este traductor) encola un Message y listo, sin Task de por medio. La Task con status/artifacts recién aparece cuando el trabajo es largo y el agente necesita ir informando avances — ver la sección siguiente.

Trazado real

Una corrida real, de punta a punta

Con agente_servidor.py corriendo en una terminal, esto es lo que imprime python cliente.py "hola mundo gracias por favor" en la otra (salida real, sin editar):

  1. descubrir_agente()

    A2ACardResolver(...).get_agent_card() hace el GET /.well-known/agent-card.json y lo deserializa a un objeto AgentCard tipado. El cliente imprime el nombre y las skills — todavía no mandó ningún dato de la tarea.

  2. enviar_mensaje() — ClientFactory

    ClientFactory(ClientConfig(...)).create(card) arma un cliente que ya sabe hablarle a la URL y el transporte que declaró la Agent Card — nunca hardcodeados.

  3. el servidor — AgentExecutor.execute()

    context.get_user_input() saca el texto del Message entrante; traducir() lo procesa; event_queue.enqueue_event(new_agent_text_message(...)) encola la respuesta. El SDK se encarga de convertir eso en el JSON-RPC de vuelta.

  4. el cliente lee las parts

    client.send_message(mensaje) es un async for: para este agente llega un único evento, un Message, del que se leen las parts de texto.

Salida real de la terminal

[cliente] Agent Card descubierta: traductor_a2a - Traduce frases simples de espanol a ingles...
[cliente]   skill: traducir_es_en (Traduce palabra por palabra usando un vocabulario chico de demo.)
[cliente] Enviando mensaje -> "hola mundo gracias por favor"

--- Resultado ---
hello world thank you for favor

Cómo correrlo

Dos terminales

# una sola vez: instalar el SDK oficial
cd orquestacion/a2a-demo
pip install -r requirements-a2a.txt

# Terminal 1
python agente_servidor.py

Qué hace el SDK, qué escribimos nosotros

Dónde termina el protocolo y empieza la lógica del agente

Todo agente_servidor.py se reduce a implementar AgentExecutor (un método execute() y un cancel()). Todo lo demás —serializar el Agent Card, exponer /.well-known/agent-card.json, parsear el JSON-RPC, validar el Message entrante, armar la respuesta— lo resuelve A2AStarletteApplication + DefaultRequestHandler. Eso es lo que compra usar el SDK oficial en vez de reimplementar el protocolo a mano.

Dicho eso, esta demo sigue siendo deliberadamente chica. El spec real de A2A define bastante más, que acá no se ejercita porque el agente siempre responde al toque:

Streaming: message/stream con Server-Sent Events, para Tasks largas que van mandando actualizaciones parciales — acá ClientConfig(streaming=False).

Ciclo de vida de la Task: working, input-required (el agente pide más datos a mitad de tarea), tasks/get para consultarla después. El SDK lo soporta (TaskUpdater, InMemoryTaskStore); este agente no lo usa porque nunca llega a crear una Task.

Auth y push notifications: autenticación sobre el transporte, y tasks/pushNotificationConfig para avisar por webhook. Tampoco cubiertos acá.

Sobre la versión: se fija a2a-sdk<1.0 a propósito. La serie 1.x reescribió los tipos centrales (AgentCard, Message, Task...) sobre protobuf en vez de los modelos pydantic de 0.x que usa este archivo — cambia bastante la forma del código. Tampoco usamos A2AClient (que en 0.3.x ya sale deprecado a favor de ClientFactory, que es lo que usa cliente.py).

Los primeros tres son intercambiables entre sí (todos resuelven "¿qué agente corre y en qué orden?" dentro de un programa). A2A resuelve otra pregunta — "¿cómo hablo con un agente que no corre en mi programa?" — y por eso puede combinarse con cualquiera de los otros tres: el servidor de este ejemplo podría, puertas adentro, ser un grafo de LangGraph.

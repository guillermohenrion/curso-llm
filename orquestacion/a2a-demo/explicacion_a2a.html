A2A: agentes que se hablan entre procesos distintos

Los tres ejemplos anteriores viven todos adentro de un mismo proceso Python. A2A (Agent2Agent) resuelve un problema distinto: cómo hacen dos agentes que corren en procesos, máquinas o hasta frameworks diferentes para hablarse, sin que uno conozca el código interno del otro. Acá va la versión más chica posible del protocolo, con la librería estándar de Python.

cliente agente remoto (servidor) contrato (Agent Card / JSON) estado de la Task

La diferencia real

No es "otro patrón de grafo" — es cruzar un proceso

En multiagente_langgraph.py o el generador_critico_langgraph.py, "supervisor" y "agente" son dos funciones de Python en el mismo proceso, que se pasan un diccionario en memoria. En A2A, cada agente es un servicio HTTP aparte: no hay memoria compartida, no hay import — todo lo que un agente sabe del otro es su URL y su Agent Card. Por eso A2A no compite con LangGraph: se puede envolver un grafo entero de LangGraph adentro de un servidor A2A y exponerlo hacia afuera como un agente más.

Las dos piezas

Agent Card (descubrimiento) + JSON-RPC (invocación)

Todo A2A se reduce a dos intercambios HTTP. Primero el cliente descubre al agente pidiendo su Agent Card — un JSON público con su nombre, sus skills y la URL a la que hay que hablarle. Después lo invoca mandándole un mensaje por JSON-RPC 2.0 con el método message/send, y el servidor responde con una Task.

Anatomía del mensaje

Lo que viaja por la red, tal cual

Agent Card — GET /.well-known/agent-card.json

{
  "name": "traductor_a2a",
  "description": "Traduce frases simples de espanol a ingles (vocabulario de demo).",
  "url": "http://127.0.0.1:9000/",
  "capabilities": { "streaming": false, "pushNotifications": false },
  "skills": [
    { "id": "traducir_es_en", "name": "Traducir espanol a ingles",
      "tags": ["traduccion", "demo"], "examples": ["hola mundo"] }
  ]
}

Request — POST / (JSON-RPC 2.0, método message/send)

{
  "jsonrpc": "2.0", "id": "9f2c...",
  "method": "message/send",
  "params": {
    "message": {
      "role": "user",
      "parts": [{ "kind": "text", "text": "hola mundo gracias" }]
    }
  }
}

Response — la Task que devuelve el servidor

{
  "jsonrpc": "2.0", "id": "9f2c...",
  "result": {
    "id": "70a1d94d-...",
    "status": { "state": "completed" },
    "artifacts": [{
      "name": "traduccion",
      "parts": [{ "kind": "text", "text": "hello world thank you" }]
    }]
  }
}

El id del JSON-RPC va y vuelve igual (así el cliente sabe a qué pedido corresponde cada respuesta); el id de la Task es otro, generado por el servidor, y sirve para consultarla después si el protocolo soportara estados intermedios (acá no: siempre responde ya completed).

Trazado real

Una corrida real, de punta a punta

Con agente_servidor.py corriendo en una terminal, esto es lo que imprime python cliente.py "hola mundo gracias por favor" en la otra (salida real, sin editar):

  1. descubrir_agente()

    GET /.well-known/agent-card.json. El cliente imprime el nombre del agente y sus skills — todavía no mandó ningún dato de la tarea.

  2. enviar_mensaje(card, texto)

    Arma el message/send con la URL que trajo la Agent Card (card["url"]) — nunca hardcodeada en el cliente.

  3. el servidor procesa y responde

    do_POST lee las parts del mensaje, llama a traducir() y arma una Task nueva con status.state = "completed".

  4. el cliente lee el artifact

    Extrae task["artifacts"][0]["parts"][0]["text"] y lo imprime como resultado final.

Salida real de la terminal

[cliente] Agent Card descubierta: traductor_a2a - Traduce frases simples...
[cliente]   skill: traducir_es_en (Traduce palabra por palabra...)
[cliente] Enviando Task -> "hola mundo gracias por favor"
[cliente] Task 70a1d94d-1114-445a-a1aa-dfee16e442cd -> status=completed

--- Resultado ---
hello world thank you for favor

Cómo correrlo

Dos terminales, cero dependencias

Solo librería estándar de Python — sin pip install, sin Ollama, sin SDK de A2A.

# Terminal 1
cd orquestacion/a2a-demo
python agente_servidor.py

# Terminal 2
cd orquestacion/a2a-demo
python cliente.py "hola mundo gracias por favor"

Honestidad del ejemplo

Qué le falta para ser A2A "completo"

Esta implementación cubre el flujo feliz de message/send para que el protocolo se vea entero en ~150 líneas. El spec real de A2A define bastante más, que acá se dejó afuera a propósito:

Streaming: message/stream con Server-Sent Events, para Tasks largas que van mandando actualizaciones parciales.

Estados intermedios: working, input-required (el agente pide más datos a mitad de tarea), tasks/get para consultar el estado después.

Auth y push notifications: autenticación (API key / OAuth) sobre el transporte, y tasks/pushNotificationConfig para que el servidor avise por webhook cuando termina.

Para un caso real, conviene el SDK oficial (a2a-sdk en Python) en vez de reimplementar el JSON-RPC a mano como acá.

Los primeros tres son intercambiables entre sí (todos resuelven "¿qué agente corre y en qué orden?" dentro de un programa). A2A resuelve otra pregunta — "¿cómo hablo con un agente que no corre en mi programa?" — y por eso puede combinarse con cualquiera de los otros tres: el servidor de este ejemplo podría, puertas adentro, ser un grafo de LangGraph.
